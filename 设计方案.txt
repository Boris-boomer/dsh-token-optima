# dsh-token-optima 可靠方案

## 一、方案定位与核心原则

本项目定位为**DeepSeek API 的 Token 归因与上下文优化插件**，运行于 DSH Cordis 插件框架。核心设计原则如下：

1. **服务端真值优先**：凡是 API `usage` 能直接返回的字段，必须作为精确值使用，客户端建模只做补充
2. **维度分离**：14 类 Token 不在同一维度上，底层采用坐标式归因模型
3. **费率外挂**：核心只解析 Token，费率作为独立可插拔模块
4. **显式标注**：每个数据点标注为「实测」「推断」或「估算」
5. **隐私默认本地**：遥测 opt-in，不记录 prompt 原文


## 二、技术事实基础

### 2.1 DeepSeek API 可用真值字段

DeepSeek Chat Completions API 的 `usage` 对象直接返回以下字段：

| 字段 | 含义 | 精确度 |
|---|---|---|
| `prompt_tokens` | 输入总 token 数 | 精确 |
| `prompt_cache_hit_tokens` | 输入中命中缓存的 token 数 | 精确 |
| `prompt_cache_miss_tokens` | 输入中未命中缓存的 token 数 | 精确 |
| `completion_tokens` | 输出总 token 数 | 精确 |
| `completion_tokens_details.reasoning_tokens` | 推理 token 数（部分模型支持） | 精确 |

约束：`prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens`。

**关键结论**：第 10 类（缓存命中输入）和第 12 类（缓存未命中输入）是 **API 真值**，无需客户端推断。这是方案最可靠的数据基础。

### 2.2 缓存机制事实

DeepSeek 上下文硬盘缓存对所有用户默认开启，每条缓存前缀是独立完整单元，后续请求必须完整匹配缓存前缀单元才能命中。缓存系统以 **64 tokens 为一个存储单元**，不足 64 tokens 的内容不会被缓存。在长输入中，系统以固定 token 间隔截取缓存前缀单元。

**关键结论**：客户端缓存片段级归因应以 64 token 为基本切分粒度，且只做块粒度的命中/未命中判定。

### 2.3 推理 Token 回传规则

当请求携带 `tools` 参数时，后续所有请求**必须完整回传**历史轮次的 `reasoning_content`，否则 API 返回 400 错误。未携带 `tools` 时无需回传。

**关键结论**：推理 token 在生命周期中会从「输出侧」迁移到「输入侧」，归因引擎必须记录这一迁移，UI 需区分「本轮新产生」和「历史回传」。

### 2.4 缓存写入计费事实

DeepSeek **不单独收取缓存写入费用**。缓存写入在计费口径上已包含在「缓存未命中」单价中。原方案将「缓存写入」作为独立计费类目，在 API 层面无对应真值。

**关键结论**：第 11 类应重新定义为「前缀写入候选」，仅作为行为追踪指标，不参与计费。


## 三、Token 坐标式归因模型

### 3.1 底层模型

每个 token 分配一个坐标：

```
token_coordinate = (source, cache_status, direction, is_reasoning)
```

- **source**（来源）：system / tools_schema / agents_md / skills / mcp_tools / user_msg / assistant_msg / tool_result / injected_ctx
- **cache_status**（缓存状态）：hit / miss / write_candidate
- **direction**（方向）：input / output
- **is_reasoning**（是否推理）：true / false

14 类只是这个坐标空间的**投影视图**，不是底层模型。底层模型干净后，各视图之间不会重复计数。

### 3.2 14 类的映射与可解析性

| 编号 | 类别 | 坐标映射 | 可解析性 |
|---|---|---|---|
| 1 | 系统提示词 | source=system, direction=input | 客户端编码 |
| 2 | 工具 Schema | source=tools_schema, direction=input | 客户端编码 |
| 3 | AGENTS.md 链 | source=agents_md, direction=input | 客户端编码 |
| 4 | 技能目录 | source=skills, direction=input | 客户端编码 |
| 5 | MCP 工具面 | source=mcp_tools, direction=input | 客户端编码 |
| 6 | 用户消息 | source=user_msg, direction=input | 客户端编码 |
| 7 | 助手回复（历史） | source=assistant_msg, direction=input | 客户端编码 |
| 8 | 工具结果 | source=tool_result, direction=input | 客户端编码 |
| 9 | 注入的上下文 | source=injected_ctx, direction=input | 客户端编码 |
| 10 | 缓存命中输入 | cache_status=hit, direction=input | **API 真值** |
| 11 | 缓存写入 | cache_status=write_candidate | **推断**（API 无字段） |
| 12 | 缓存未命中输入 | cache_status=miss, direction=input | **API 真值** |
| 13 | 模型输出 | direction=output, is_reasoning=false | **API 真值**（completion - reasoning） |
| 14 | 推理 Token | direction=output, is_reasoning=true | **API 真值**（部分模型） |

### 3.3 归因算法流程

每次请求的生命周期如下：

**阶段一：请求组装前（精确计数）**

对第 1–9 类内容逐段用 DeepSeek 原生 tokenizer 编码计数。DeepSeek 使用自定义 Byte-level BPE tokenizer，128K 词汇表，与 OpenAI cl100k_base 完全不同。需使用与 DeepSeek 一致的 tokenizer 实现（如 `deepseek-moby-wasm` 或 `@tlibnx/tokenizer-deepseek_v4_flash`）。

**阶段二：请求发出后（获取真值）**

从 API 响应的 `usage` 中提取：
- `prompt_cache_hit_tokens` → 第 10 类精确值
- `prompt_cache_miss_tokens` → 第 12 类精确值
- `completion_tokens` → 第 13+14 类总和
- `reasoning_tokens`（如有）→ 第 14 类精确值；否则客户端对 `reasoning_content` 编码推断

**阶段三：片段级归因（对齐校准）**

API 只给缓存命中/未命中的**总量**，不告诉哪条消息命中多少。片段级归因流程：

1. 对第 1–9 类内容按实际序列化后的 token ID 序列构建前缀哈希
2. 按 64 token 块粒度切分，标记哪些块与上一轮相同（命中候选）
3. 统计命中候选块的 token 总数
4. 与 `prompt_cache_hit_tokens` 对齐：若偏差超过阈值（如 ±3%），优先信任 API 真值，将残差归入「未归因」桶
5. 按块粒度将命中/未命中分配到各来源

**阶段四：推理 Token 生命周期追踪**

当请求携带 `tools` 时，本轮的 `reasoning_content` 必须保存并在下一轮回传。归因引擎记录：

- 本轮产生：`direction=output, is_reasoning=true`
- 下轮回传：`direction=input, source=assistant_msg, is_reasoning=true`

UI 中推理 token 显示两个数字：**本轮新产生**和**历史回传**。


## 四、缓存建模引擎

### 4.1 前缀哈希

对实际序列化后的 token ID 序列计算哈希，而非原始文本。哈希键包含：

```
hash_key = SHA256(
  model_id + api_version + tokenizer_version +
  tools_schema_hash + system_prompt_hash +
  serialized_prefix_token_ids
)
```

必须处理：工具 JSON key 顺序固定、时间戳/随机 ID 去除、会话分支隔离。

### 4.2 64 token 块粒度

按官方 64 token 存储单元切分缓存块。每次请求：

- 对每个 64 token 块计算哈希
- 与上一轮对应位置的块哈希比对
- 相同 → 命中候选；不同 → 未命中
- 新增块（超出上一轮长度）→ 写入候选

### 4.3 缓存失效事件标记

以下事件会导致前缀缓存失效，必须在监控面板中显式标记：

- System prompt 变更
- 工具 Schema 变更（内置或 MCP）
- 模型切换
- 64 token 块边界对齐变化
- 中间消息编辑/压缩

### 4.4 缓存写入候选的推断

第 11 类「缓存写入」无 API 真值，定义为：

> 首次出现、且长度 ≥ 64 tokens 的前缀块，在下一轮中若被完整匹配则成为命中，否则为写入候选。

该值标注为**推断**，不参与计费计算，仅用于观察缓存预热效率。


## 五、上下文优化策略

### 5.1 压缩的三层语义

「无损压缩」需要拆分定义：

| 层级 | 含义 | 实现 |
|---|---|---|
| **存储无损** | 原始消息永久保留，可回溯 | 本地 SQLite 存储原始消息 |
| **上下文有损** | 送给模型的是压缩表示 | DAG 摘要节点替代原始内容 |
| **可逆展示** | UI/工具可按需展开原始节点 | 通过 `context_audit` 工具展开 |

**禁止压缩白名单**：最新用户消息、工具调用 ID、工具参数、最终答案、文件路径、代码块。

### 5.2 压缩触发条件

压缩仅在上下文即将超出缓存窗口时触发，且只压缩**尚未被缓存的前缀单元**。已缓存前缀保持原样，确保后续请求继续命中。

### 5.3 DAG 裁剪三遍法

1. **剥离机械膨胀**：去除工具输出中的重复日志、大段文件内容，保留结构化摘要
2. **摘要低密度段**：对低信息密度段落生成摘要节点
3. **聚合高层节点**：将摘要节点聚合为更高层节点

压缩事件必须记录：压缩前各类 token 数、压缩后各类 token 数、受影响类别、缓存命中率变化。

### 5.4 推理强度动态调整

`reasoning_effort` 有效值为 `low / high / max`，默认 `high`。根据任务复杂度自动切换：

- 简单任务（格式整理、信息提取）→ `low`
- 复杂推理任务 → `high` 或 `max`

任务分类器需通过 A/B 测试验证任务成功率，不能只追求省 token。

### 5.5 思维链剪枝

在压缩阶段对历史轮次思维链做信息密度评估，只保留包含关键决策、发现、结论的推理段，删除重复探索和失败路径。剪枝后必须验证任务成功率。


## 六、系统架构

### 6.1 模块分层

```
dsh-token-optima/
├── packages/
│   ├── core/                    # 核心算法层（零 DSH 依赖，纯 TS）
│   │   ├── tokenizer/           # DeepSeek WASM tokenizer 适配
│   │   ├── cache-model/         # 64 token 块前缀缓存建模
│   │   ├── attribution/         # 坐标式归因引擎
│   │   ├── compressor/          # DAG 压缩器
│   │   └── types/               # 坐标模型类型定义
│   ├── host/                    # DSH Host 半
│   │   ├── interceptors/        # 请求拦截与来源标记
│   │   ├── registry/            # 归因结果注册表
│   │   └── tools/               # context_audit / token_report
│   ├── client/                  # Web UI 半
│   │   ├── panels/              # 圆环面板 / 趋势图
│   │   └── cards/               # 逐请求明细
│   └── pricing/                 # 费率适配器（独立可插拔）
├── tests/
└── docs/
```

### 6.2 DSH 插件接口

遵循 DSH Cordis 插件规范：导出 `apply(ctx, config)` 函数，通过 `inject: ['tools']` 声明依赖，使用 `Schema.object` 定义配置 schema，通过 `ctx.tools.register(defineTool({...}))` 注册工具。

注册两个只读工具：

- **`context_audit`**：展开指定消息的原始内容（用于验证压缩可回溯性）
- **`token_report`**：返回当前会话的 14 类 Token 归因数据

### 6.3 Host/Client 通信

- 协议版本化 + 能力协商
- Host 推送使用 SSE/WebSocket + 批量事件
- Client 不直接访问 Host 内部状态

### 6.4 Tokenizer 加载策略

优先使用 DeepSeek 原生 tokenizer 的 WASM 编译版本（如 `deepseek-moby-wasm`），128K 词汇表。降级链：

1. WASM tokenizer（精确）
2. 纯 TS 重写的 BPE 实现（较精确）
3. 字符估算（精度约 80–90%，显示警告）


## 七、测试策略

### 7.1 测试分层

| 层级 | 内容 | 工具 |
|---|---|---|
| 单元测试 | tokenizer 精度、前缀哈希、64 token 块切分、DAG 裁剪 | Vitest |
| 属性测试 | 前缀哈希幂等性、压缩边界、块对齐 | fast-check |
| 契约测试 | 插件 `apply` 函数、`inject` 声明、Config schema | DSH 插件测试模式 |
| 生命周期测试 | 一次性 Docker 安装精确版本 DSH，验证加载/卸载 | `dsh-testkit` |
| A/B 差分测试 | 优化前/后同任务对比 14 类归因数据 | `dsh-plugin-abtest` |
| 录制回放 | 录制真实 API 响应，离线回放 | 自定义 middleware |

### 7.2 关键测试用例

- **缓存命中精确性**：相同前缀追加消息，断言命中块哈希与上一轮一致
- **缓存失效正确性**：中间消息变更，断言从变更点后所有块未命中
- **压缩可回溯性**：压缩后所有用户消息和正式回复逐字保留，原始内容可通过 `context_audit` 展开
- **归因对齐**：客户端估算的命中/未命中与 API `usage` 偏差 < 3%
- **推理回传完整性**：携带 `tools` 时，`reasoning_content` 完整保存并在下一轮回传，不触发 400 错误

### 7.3 统计要求

A/B 测试固定模型版本、温度、seed，使用统计显著性检验。归因精度分类型给出误差和置信区间，而非全局 ±5%。


## 八、隐私与安全

1. **默认本地处理**：所有 Token 归因计算在本地完成，OTLP 遥测 opt-in
2. **不记录 prompt 原文**：只存哈希、token 数、类型标签
3. **哈希加盐**：防字典攻击
4. **数据 TTL**：归因数据可配置保留期限，支持删除和导出
5. **路径安全**：所有缓存数据写入 DSH profile 目录内专用子目录，做路径遍历和符号链接防护
6. **权限最小化**：只注册两个只读工具，不修改沙箱、审批或凭证配置
7. **依赖最小化**：核心算法层零运行时依赖，提供 SBOM，发布使用 OIDC trusted publishing

文档需包含 `PRIVACY.md`、`SECURITY.md`、`THREAT_MODEL.md`。


## 九、可观测性

### 9.1 自身遥测

基于 OpenTelemetry 导出 trace/log/metric。每次请求拦截产生一个 span，属性包括：

- 14 类 Token 各自数量
- 缓存命中/未命中比例
- 压缩事件（前/后各类 token 数）
- 推理强度设置
- 归因置信度

**高基数治理**：工具名、会话 ID 不放 metric label，只放 trace/log 或聚合后展示。

### 9.2 用户侧可视化

- **圆环面板**：当前上下文 14 类构成占比，分组显示（输入/输出/缓存/推理/工具）
- **趋势图**：逐请求堆叠条，标记压缩事件（✂）和缓存失效事件（⚡）
- **推理双数字**：本轮新产生 + 历史回传
- **数据来源标注**：实测/推断/估算用不同视觉样式区分
- **导出**：CSV/JSON

### 9.3 预算告警

支持会话/日/月预算设置，超支可触发降级策略（降低推理强度或提高压缩级别）。


## 十、性能预算

放弃「零性能影响」的不现实承诺，改为可测量的性能预算：

| 指标 | 目标 |
|---|---|
| P95 拦截开销 | < 5ms |
| CPU 增量 | < 1% |
| 内存上限 | 可配置，默认 256MB |
| 归因计算 | 异步，不阻塞请求路径 |
| WASM 加载 | 超时自动降级 |

归因计算在请求发出后异步执行，不增加首 Token 延迟。使用 Worker 隔离 + 背压队列。

## 十三、生产健壮性

1. **优雅降级**：tokenizer 加载失败时回退到字符估算，显示警告，不阻塞 DSH 运行
2. **看门狗**：插件启动注册守卫，初始化超时自动禁用并回滚配置
3. **熔断**：压缩算法连续 3 次异常自动切换纯监控模式
4. **幂等性**：重复安装/卸载不残留状态，配置文件写入前备份
5. **配置原子写**：配置文件使用原子写入 + 文件锁 + 备份轮转

## 十五、与原始方案的核心差异

| 维度 | 原始方案 | 可靠方案 |
|---|---|---|
| 归因真值来源 | 客户端建模为主 | **API usage 真值优先**，建模补充 |
